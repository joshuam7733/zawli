# Security

Security is part of the product: restaurants trust Zawli with their sales and staff, and one restaurant must never see another's data.

## Threat model (summary)

| Actor                          | Can                                                                               | Must not                                                                                           |
| ------------------------------ | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Anonymous guest with a QR code | read that branch's menu, order for that table, call staff, follow their own order | see other tables' orders, change prices, reach admin screens, order after the code is revoked      |
| Restaurant staff               | act within their role and branches                                                | read or change another restaurant, exceed their role (e.g. kitchen → money), act on other branches |
| Owner                          | administer their restaurant                                                       | administer the platform or another restaurant                                                      |
| Platform staff                 | platform work by platform role                                                    | (billing/support roles) manage tenants beyond their permission                                     |
| Network attacker / other sites | —                                                                                 | forge requests (CSRF), steal sessions, brute-force sign-in, inject scripts                         |

## Controls

**Tenant isolation** (see ARCHITECTURE → Multi-tenancy): composite foreign keys in the database, tenant-scoped queries in every service, membership-gated contexts, NOT_FOUND for other tenants' ids. Covered by `tests/integration/tenant-isolation.test.ts` (menu, prices, orders, tickets, payments, bills, waiter calls, print jobs, tables/QR, staff, invoices, reports/exports, cross-tenant FK rejection, branch-level isolation, role restrictions).

**Authentication** — Better Auth email/password. Passwords hashed with scrypt; min 10 chars with letters and a digit; sign-in rate-limited (8/min per IP+path); DB-backed sessions, 12 h expiry, `httpOnly`, `SameSite=Lax`, `Secure` in production; deactivated users cannot create sessions and are rejected on every request. Public sign-up is disabled. First login and password resets use one-time setup links (192-bit random, SHA-256 hashed at rest, 72 h expiry, single use, all sessions revoked after use). No email provider is used in V1 — links are shown once to the inviting admin/owner to deliver privately.

**Authorization** — role → permission matrix (`src/domain/permissions.ts`), checked server-side in services (`requirePermission`, `requirePlatform`). Kitchen staff never receive prices or payments (fields are stripped server-side). Managers cannot create owners or managers; owners are managed by the platform. Platform routes return 404 to non-platform users.

**QR tokens** — 144-bit random, URL-safe; shape-checked before any DB lookup; must be ACTIVE and belong to an active table, branch and live tenant. Regenerate/revoke takes effect immediately. Sequential ids are never used as credentials. Customer order tracking uses a separate 192-bit token.

**Input & output** — Zod schemas on every service input; client prices ignored; React escapes output; the only `dangerouslySetInnerHTML` is QR SVG generated by our own code from our own URL; CSV export neutralises formula injection (`=`, `+`, `-`, `@`).

**CSRF** — Server Actions are origin-checked by Next.js; JSON API mutations require a same-origin `Origin`/`Referer` (`assertSameOrigin`); Better Auth checks origins on its endpoints; cookies are `SameSite=Lax`.

**Rate limiting** — sign-in (Better Auth), order placement (30/10 min per IP, 60/10 min per QR token), waiter calls (12/10 min), order tracking (240/min), uploads, print bridge. The limiter is in-memory: correct for one instance. **With multiple instances, move it to Redis or Postgres** (same `rateLimit()` signature).

**Uploads** — images only (JPEG/PNG/WebP detected by magic bytes, never by name/MIME), ≤ 2 MB, random file names, SVG rejected, served with `nosniff` and a `default-src 'none'` CSP.

**HTTP headers** — CSP (`frame-ancestors 'none'`, `object-src 'none'`, `form-action 'self'`), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy`, `Permissions-Policy`, HSTS in production, no `X-Powered-By`. Setup/QR pages use `referrer: no-referrer`. The CSP still allows inline scripts (Next.js hydration); moving to nonces is on the roadmap.

**Audit log** — tenant creation/status, subscription changes, invoices and invoice payments, staff invites/role changes/deactivation, setup links issued, menu price changes, settings changes, table/QR changes, order cancellations, payments recorded/voided, printer keys. Metadata is scrubbed of keys that look like passwords/tokens/secrets.

**Secrets** — only in environment variables; `.env` is git-ignored; `.env.example` has placeholders. Print-bridge keys and setup tokens are stored hashed and shown once. Logs never include passwords, tokens or cookies (`src/server/log.ts`).

**Least privilege (deployment)** — run migrations with an owner role; run the app with a role that has DML only (no DDL). Restrict database network access to the app.

## Suspension rules

| Tenant status | Staff sign-in | Changes                           | QR ordering              | Data                                 |
| ------------- | ------------- | --------------------------------- | ------------------------ | ------------------------------------ |
| ONBOARDING    | yes           | yes                               | no ("not taking orders") | kept                                 |
| ACTIVE        | yes           | yes                               | yes                      | kept                                 |
| SUSPENDED     | yes           | **read-only** (view + CSV export) | no                       | kept                                 |
| DEACTIVATED   | no            | no                                | no                       | kept (export by platform on request) |

## Known gaps (tracked in ROADMAP)

- No MFA yet (recommended first for platform admins).
- Rate limiter is per-instance.
- CSP uses `'unsafe-inline'` for scripts.
- No Postgres row-level security (isolation relies on composite FKs + service scoping + tests).
- No automated dependency/vulnerability scanning in CI yet (no CI configured).

## Reporting a vulnerability

Contact the platform team privately; do not open public issues for security problems.
